# Deploying `server.js` to Railway

This repo ships a small Express server, `server.js`, as an optional way to self-host the VDO.Ninja client on a platform like [Railway](https://railway.app) instead of a plain static host. It serves the exact same files as the reference NGINX config in [`install.md`](install.md) — same clean-URL behavior, same CORS headers — and adds a few opt-in, environment-variable-driven extras: deploy-time config injection (`/config.js`), a theme overlay, a gated "director link" route, request logging, and a per-IP rate limiter.

This document is only about the Node/Express deploy model. For plain static hosting (GitHub Pages, NGINX, "internet-free" LAN deployments), see [`install.md`](install.md). For running your own TURN relay, see [`turnserver.md`](turnserver.md) — `server.js` has nothing to do with TURN beyond optionally telling the client which TURN server to use (see `TURN_SERVER` below).

## When to use this instead of GitHub Pages

VDO.Ninja's media is peer-to-peer (WebRTC) — running your own server does **not** make calls faster or more reliable. Deploying `server.js` is worth doing when you specifically want one of the things it adds over a plain static host: injecting your own TURN/signaling config or branding at deploy time via environment variables (rather than hand-editing `index.html`), serving a custom theme, or dispensing a password-gated "director" link. If you just want your own copy of the client with no server-side logic, GitHub Pages (see `install.md`) is simpler and free.

## Deploy steps

1. Push this repo (or your fork) to GitHub and connect it as a new Railway project ("Deploy from GitHub repo").
2. Railway auto-detects the Node app via Nixpacks and uses the committed `railway.json`, which:
    - runs `npm run precompress` as the build step (generates max-quality `.br`/`.gz` siblings for the large text assets — see "Precompressed assets" below), then
    - starts the server with `node server.js`.

    You don't need to configure the build/start commands yourself; `railway.json` already does it.

3. Set whichever environment variables you need (see the reference table below) in the Railway service's **Variables** tab. None are required for a basic deploy — the server runs with sane defaults if you set nothing at all.
4. Deploy. Railway assigns a public URL (or attach your own domain); the client is served from `/`.

## Recommended Railway settings

- **Do not set `PORT`.** Railway injects its own `PORT` value into the environment automatically, and `server.js` already reads `process.env.PORT`, only falling back to `8366` when nothing usable is supplied. Setting it yourself risks it not matching the port Railway actually routes traffic to.
- **Set `TRUST_PROXY=1`.** Railway puts exactly one proxy hop in front of your service. Left at the default (`loopback`), the server only trusts `X-Forwarded-*` headers from `127.0.0.1`/`::1`, so behind Railway's proxy every client's `req.ip` collapses to the same value — the F11 access log (`LOG_REQUESTS`) would show one IP for everyone, and the rate limiter (below) would throttle all your visitors as a single shared bucket. Get it wrong in the other direction (trusting more hops than actually exist) and a client could spoof `X-Forwarded-For` to fake its own IP. `TRUST_PROXY=1` — trust exactly one hop — is the correct value for Railway's topology.
- **Set the healthcheck path to `/healthz`.** In the service's **Settings → Healthcheck Path**, use `/healthz`. It's a lightweight, always-`Cache-Control: no-store` JSON endpoint purpose-built for this (see below) — no need to point Railway's probe at `/` instead.

## Optional features

### Director link

Setting **both** `DIRECTOR_SECRET` and `DIRECTOR_ROOM` enables a `/director` route. It's HTTP Basic-auth protected — any username, password must match `DIRECTOR_SECRET` — and on success 302-redirects to `/?director=<DIRECTOR_ROOM>`, with `ROOM_PASSWORD`/`ROOM_KEY` (if set) folded into the URL's `#` fragment so they never appear in a query string or in `LOG_REQUESTS`' access log. Setting `ROOM_KEY` also adds `&requireapproval` to the link.

This route only _dispenses_ the link — it can't itself enforce the director role or room membership; that's still handled by the signaling server (`wss.vdo.ninja` by default, or your own via `SIGNALING_HOST`). In practice: give trusted collaborators a URL like `https://your-app.up.railway.app/director` and a shared password; they log in once with Basic auth and land on the privileged director view for `DIRECTOR_ROOM`.

Setting only one of `DIRECTOR_SECRET`/`DIRECTOR_ROOM` disables the feature (the route is absent, not just always-401). Setting `DIRECTOR_SECRET` without `DIRECTOR_ROOM` also logs a one-time warning; setting `DIRECTOR_ROOM` without `DIRECTOR_SECRET` disables the feature the same way but currently logs nothing.

### Rate limiting

`RATE_LIMIT_RPM` enables a lightweight, in-memory, per-IP sliding-window limiter — a basic abuse/DoS backstop for a deploy with nothing else in front of it. It is **off by default**.

If you do enable it, **set it generously (a few hundred, not a handful)**. A single browser page load fans out into many requests — `index.html`, `lib.js`, `webrtc.js`, `adapter.js`, CSS, icons, `manifest.json`, translation files, and more — and every one of those counts against the same per-minute budget. A limit tuned for "number of user actions per minute" will 429 normal page loads. `/healthz` is always exempt so Railway's health probe is never throttled. If you're already running behind Cloudflare or another CDN/WAF, rate-limiting there is generally a better place to do it (blocked before it reaches this process, and not reset by every restart the way this in-memory limiter is).

## Precompressed assets

The build step (`npm run precompress`, already wired into `railway.json`) generates maximum-quality Brotli (`.br`) and gzip (`.gz`) siblings for the repo's large text assets (`lib.js`, `webrtc.js`, CSS, etc.) at deploy time. `server.js` serves those precomputed files directly to clients that support Brotli/gzip instead of paying an on-the-fly compression cost on every request. There's nothing you need to configure for this — it happens automatically as part of the Railway build.

## Other notes

- `/config.js` and `/theme.css` are regenerated from the live environment on every request (not baked in at build time), so changing an env var and redeploying is enough to pick up a new TURN server, signaling host, brand name, or theme.
- `server.js` itself, `node_modules/`, `package.json`, `package-lock.json`, and a few internal files are never served as static assets, regardless of environment configuration.
- For TURN/STUN server setup, see [`turnserver.md`](turnserver.md). For GitHub Pages / NGINX static hosting and "internet-free" LAN deployments, see [`install.md`](install.md).
